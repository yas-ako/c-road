# C\*-road 開発方針

> この文書はソースコードの設計と実装方針を記録する。正式なゲームルールは [rules.md](rules.md) を参照する。

## 基本方針

- ゲームルールを Vue と Pinia から分離する。
- 局面は TypeScript のデータ型で表現し、ルールは純粋関数として実装する。
- 局面を直接変更せず、操作の結果として新しい局面を返す。
- Pinia は確定した局面の保持と、UI からゲームエンジンへの操作の受け渡しを担当する。
- 対戦形式ごとの初期配置と勝利判定は、共通エンジンから分離する。
- 将来の CPU 対戦で仮想局面を安全に評価できる設計にする。
- クラス継承を中心とせず、型、データ、関数を中心に構成する。

## データモデル

現在の「正数は青、負数は赤、0は空きマス」という表現は、街を追加する際に判別可能な型へ移行する。

```ts
type PlayerColor = "blue" | "red";

type Coordinate = Readonly<{
  x: number;
  y: number;
}>;

type Cell =
  | Readonly<{ kind: "empty" }>
  | Readonly<{ kind: "road"; color: PlayerColor; level: number }>
  | Readonly<{ kind: "town"; townId: TownId }>;
```

街はどちらの色にも属さないため、`town` のセルには色や所有者を持たせない。対戦形式の正式名称は未確定であるため、コード上の識別子も外部に公開する API として固定しない。

## ゲームエンジン

エンジンは少なくとも次の操作を提供する。型名と関数名は実装時に調整できるが、責務の境界は維持する。

```ts
function createGame(mode: GameMode): GameState;

function getLegalActions(state: GameState): readonly GameAction[];

function validateAction(state: GameState, action: GameAction): ValidationResult;

function applyAction(state: GameState, action: GameAction): ApplyActionResult;
```

`applyAction` は元の局面を変更せず、確定後の局面と発生したイベントを返す。不正な操作は UI だけでなくエンジン側でも拒否する。

```ts
type ApplyActionResult = {
  state: GameState;
  events: readonly GameEvent[];
};

type DemolitionEvent = {
  type: "demolition";
  boardBeforeDemolition: Board;
  removedCells: readonly Coordinate[];
};
```

取り壊しが発生する場合、`state` には取り壊し後の確定局面を入れる。`DemolitionEvent` には、道を置いた後かつ取り壊し前の盤面と、取り壊す座標を入れる。

対戦形式固有の処理は、共通の操作適用から呼び出す。

```ts
type ModeRules = {
  createInitialState(): GameState;
  getLegalSetupActions(state: GameState): readonly GameAction[];
  evaluateVictory(state: GameState): WinResult | null;
};
```

## 処理の順序

1手の処理順序を次に統一する。

1. 操作の合法性を検証する。
2. 道を配置した局面を作る。
3. その局面から取り壊し対象をすべて収集する。
4. 取り壊し対象の重複を除き、一括で反映する。
5. 取り壊し後の局面で勝利を判定する。
6. 勝者がいなければ引き分けを判定する。
7. 対局が続く場合は手番を交代する。

ゲームエンジンは演出待ちを行わず、次の確定局面と演出に必要なイベントを即座に返す。

## 主要アルゴリズム

### 取り壊し

道を配置した直後の盤面を読み取り専用の入力として、盤面全体を8方向に探索する。探索中に盤面を書き換えない。

見つけた対象座標を集合へ入れ、すべての探索終了後に一括で空きマスへ変更する。これにより、探索順序と重複検出が結果に影響しない。

### 街をつなぐ経路

青と赤の道路網を別々に DFS または BFS で探索する。同じ色で道路番号の差が1以下の辺だけをたどり、1つの連結成分が2つの街の両方に隣り合うかを調べる。

勝利した経路を表示できるように、探索時に各マスの親を記録する。勝利結果には、経路上のマスだけでなく接続辺も保存する。

### 有効な周回路

青と赤の道路網を別々に DFS または BFS で探索する。すべての経路を列挙する必要はない。

各論理マスに、トーラスの折り返しを行わない仮想座標を記録する。未探索のマスには、移動方向から計算した仮想座標を記録する。

探索済みのマスへ到達した場合は、記録済みの仮想座標と、今回の経路から期待される仮想座標を比較する。一致する場合は通常の接続または収縮可能な閉路である。異なる場合は有効な周回路が存在する。

異なる仮想座標の差は、盤面サイズ13の倍数になる。差が13で割り切れることを検証した上で、13で割って左右と上下の巻き数を得る。

異なる仮想座標が見つかった辺と探索木の親情報から、勝利した周回路を復元する。勝利結果にはマス、接続辺、巻き数を保存する。

盤面は169マスと小さく、取り壊しによる辺の削除もあるため、各手の解決後に再探索する。当初は Union-Find による差分管理を行わない。

## Pinia と UI の責務

### Pinia

- 現在の確定局面を保持する。
- UI から受け取った操作をゲームエンジンへ渡す。
- ゲーム開始、リセット、ページ離脱時の破棄を行う。
- 取り壊し演出などの解決中は操作を受け付けない。

### UI

- 選択中のマスと入力中の道路番号を保持する。
- 上限と取り壊しの通知を表示する。
- 取り壊しまでの待機と表示演出を担当する。
- 取り壊し演出中は、`boardBeforeDemolition` を表示して対象マスを強調する。演出終了後に Pinia が保持する確定局面の表示へ切り替える。
- 取り壊し演出中は、盤面操作と投了操作を無効にする。
- 投了は取り消せないため、実行前に確認画面を表示する。
- 勝利時に経路上のマスと接続辺を強調表示する。外周の複製マスにも強調を反映する。
- 13×13の論理座標を15×15の表示盤面へ写像する。

タイマーはゲームルールの一部にしない。ページを離れたときは局面、通知、表示用スナップショット、演出タイマーを破棄する。ゲームページへ戻った場合は新しい対局を開始する。

## CPU 対戦への備え

CPU は Pinia や UI を操作せず、ゲームエンジンの合法手生成と局面適用を利用する。

```ts
type ChooseAction = (state: Readonly<GameState>) => Promise<GameAction>;
```

各対戦形式は共通の合法手 API を提供し、評価方法だけを対戦形式ごとに差し替えられるようにする。初期実装では合法手からのランダム選択が可能な境界まで整備する。

## 実装順序

1. 現行ルールを自動テストで固定する。
2. ゲームエンジンを Vue と Pinia から分離する。
3. Pinia と現在の UI を新しいエンジンへ接続する。
4. 対戦形式ごとの初期化と勝利判定を分離する。
5. 街を使用する対戦形式を実装する。
6. 周回路を作る対戦形式を実装する。
7. CPU が利用できる合法手生成 API を確認する。
